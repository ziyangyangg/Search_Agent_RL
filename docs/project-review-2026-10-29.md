## 现在实际实现的工程

| 主题 | 旧 Search-R1 | 新 Workbench |
| --- | --- | --- |
| 动作接口 | 标签协议，多条训练/推理/评估路径 | Completion/ToolCall/Trajectory 契约与统一执行循环。 |
| 模型 | 固定模型、EOS、CUDA 假设较多 | 显式端点和模型 ID；原生工具协议，不假设旧 checkpoint 兼容。 |
| 工具 | 搜索训练是主体 | 工作区文本列表、读取、创建和明确命名的 SQLite 检索。 |
| 预算 | 部分循环与请求无上限 | 步数、调用数、输出和输入规模检查，终止原因留痕。 |
| 评估 | 某路径用 gold 选择原答案或截短答案 | 固定预测评分，失败保留分母，逐题证据与哈希。 |
| 训练 | 正式 PPO/GRPO 与独立 LoRA 策略梯度并存 | 只有来源记录导出，尚无新 trainer。 |
| Jev 协作 | 原盘主线未集成 | 已准备只读动作中的选择与生成模型升级。 |

运行时不导入 torch、transformers、vLLM 或 veRL，Python 运行依赖为空。模型端点与训练
后端是独立接口，文本轨迹不能冒充 token 对齐的 on-policy 数据。详见
[架构](architecture.md)和[RL 路线](rl-roadmap.md)。

## Jev 与 Qwen 的职责

实际设计为 **Jev 快速闭集选择 + Qwen 推理生成**。这里用 System 1/2 比喻职责，不能从
模型名字推断内部认知机制，也不要把曾经的口头简称当成相反实现。

Jev 从 JSON 中已绑定工具名和完整参数的只读候选里选择，或选 `reason` 升级。低概率、
候选不足、服务异常和状态过大会回到生成模型。它不生成任意参数、不授权写入、不撰写最终
回答。Qwen 自动规划、可复用条件计划、学习式路由与双系统 RL 均未实现。

fixture 中省一次生成调用只说明软件路径成立，不能证明真实加速。比较时，单模型也应看见
相同候选信息；同时报告任务成功、快速覆盖/条件错误、p50/p95 延迟、token 和实际费用。
具体设计见[双系统说明](dual-system.md)。

## 历史成绩应如何看待

原盘实际检查到评估集 **500 行**、小语料 **41,897 行**，15 份 `main_ppo.log` 均为
**0 字节**。权重、图表和注释不能证明训练过程或能力提升；历史 **44.80%** 缺可复核的
对应逐题结果和完整日志，状态仍为未复核。

旧训练验证与独立评估的语料、检索、解码、轮数和评分可能不同，不能拼成可靠的训练前后
提升。换强模型、换协议和 RL 更新的贡献也需分别对照。新严格 EM/F1 与旧截短择高分不同，
需要固定配置重新评估；合成样例分数只检验计算逻辑。

## 当前缺点与下一步

旧问题集中在奖励来源、gold 依赖评分、检索契约、无界请求、资源硬编码及恢复能力。
新包通过接口拆分避开部分旧路径，并提供四文件补丁；没有修完旧 `infer.py`、全部检索服务、
独立评估和 LoRA trainer。覆盖范围逐项写在[已知问题](known-issues.md)中。

新工程下一步是固定真实端点和任务 verifier，再建立可比较的质量—成本基线。随后评估 Jev
与单模型，最后接入真实 token/logprob 采样和 RL。当前 `completed` 是执行结束，不是任务
正确；应用路径检查也不等于 OS 沙箱。
