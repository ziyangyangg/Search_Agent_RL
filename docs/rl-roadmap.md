# Agent RL 研究路线与证据边界

核查日期：2026-10-22。本文依据公开论文、作者仓库与官方文档，讨论搜索 Agent 如何发展为可训练、可评估的工具 Agent。本文不采用带水印资料中的实验结论；历史“44.80%”缺少对应原始评估文件与非空训练日志，应标记为**未复核**，不能作为本仓库的已验证结果。

## 当前实现与先决条件

本包提供运行时、模型与工具接口、轨迹记录和评估；**没有实现新的 RL trainer，也没有运行新的训练实验**。`src/agent_workbench/training.py` 导出框架无关记录，并明确写入 `trainer_ready: false`：文本记录尚不包含执行 token 级策略优化所需的完整采样信息。旧 Search-R1 的修复由独立的 `scripts/patch_legacy.py` 管理，不能据此宣称已实现下面的算法。

算法比较之前，应先修复旧实现中的评估口径、动作解析、轨迹截断与掩码一致性问题，并建立可信基线。每次模型调用须记录：实际 prompt/action token IDs、采样策略 log-probabilities、策略及模板版本、工具结果边界、终止原因和工具故障。工具 observation 可以参与上下文注意力，但不能作为策略生成动作计入损失。文本重新分词不能保证重建真实采样条件。

## 哪些技术有足够证据

以下证据分三级：**A** 为同类任务与公开实现的直接证据；**B** 为相邻任务或不同模型的机制证据；**C** 为本项目尚未验证的迁移假设。论文数字保留其原始任务、模型和协议，不能与本地 500 题结果横向排名。

### 1. GiGPO：首个算法对照，证据 A

[官方仓库的 Search-R1 结果](https://github.com/langfengQ/verl-agent#results)列出 Qwen2.5-3B-Instruct：Search-R1 七个 QA 数据集平均为 **32.5**，GiGPO 为 **42.1**；HotpotQA 分别为 **32.4、36.9**。仓库提供 `examples/gigpo_trainer/run_search.sh`。[方法论文](https://arxiv.org/abs/2505.10978)将完整轨迹相对优势与共享 anchor state 下的步骤相对优势结合，无需额外 critic。

这是最贴近原模型与检索任务的候选。迁移时必须记录状态分组大小、覆盖率及相似性误合并；不同历史中的相似文本不必然表示相同决策状态。官方跨系统表格为迁移提供动机，不能替代本仓库的预算匹配重跑。

### 2. Agent Lightning v1.0：训练架构参照，证据 A/B

[2026 年技术报告 §4.1](https://arxiv.org/html/2608.17528v1)沿用 Search-R1 设定，以 Llama-3.2-3B-Instruct、GRPO 和 HotpotQA 训练，在六个 QA 数据集各抽 50 题验证，EM 从 **25.1% 到 41.7%**。其核心价值是把真实 Agent 执行框架与优化器解耦；§2.1 同时说明了重新分词破坏 token 前缀连续性的问题。[官方实现](https://github.com/microsoft/agent-lightning)可作为外部训练适配器候选。

我们应保留同一套模型、工具、上下文与控制流程进行训练和部署，避免另写一套训练专用 Agent。上述结果证明该架构能训练搜索 Agent；不证明仅替换框架就能提升当前模型，也不直接证明办公可靠性。

### 3. Rollout Correction：先测量，再决定纠正，证据 B

[verl 官方说明](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html)区分实际采样分布 `π_rollout`、训练侧旧策略 `π_old` 和待更新策略 `π_θ`。同权重在推理与训练后端中也可能给出不同概率，异步采样还会引入参数滞后。若用重算的 `π_old` 代替实际 behavior probability，普通 PPO ratio 不会自动修正这种差异；官方提供重要性加权和拒绝采样实现。

先记录 mismatch、有效样本率及权重尾部，再做 correction 消融。旧 fork 不具备这些接口，不能直接追加新版配置字段。现有证据也不足以认定本项目历史训练退化由该机制导致。

### 4. ABC-GRPO：有控制比较的步骤信用分配，证据 B

[ABSeeker 表 3](https://arxiv.org/html/2608.05102v1)在同一 ABSeeker-4B-SFT 初始化、关闭 context management 时，标准 GRPO 的 BrowseComp 为 **33.5%**，ABC-GRPO 为 **37.3%**。该比较比“37.3% 到 55.3%”更适合支撑 RL 改进判断，后者还改变了上下文管理。[公开代码](https://github.com/PolarSeeker/ABSeeker)包含线索恢复、步骤评分与训练入口。

其方法从已验证答案反向恢复线索，再评价每一步的证据进展，使失败轨迹中的有效步骤仍能获得学习信号。迁移需计算额外 judge 成本并评估评分噪声；对于文件修改、办公流程等任务，短答案线索不能直接代替可验证的应用状态与子目标。

### 5. 后续候选，证据 B/C

[SimpleTIR](https://arxiv.org/abs/2509.02479)通过过滤没有代码或最终答案的 void-turn 轨迹改善多轮工具训练稳定性；它首先支持代码执行任务中的机制判断，检索版有效性仍须验证。[GraphGPO](https://arxiv.org/abs/2605.26684)及其[公开实现](https://github.com/langfengQ/verl-agent/tree/master/recipe/GraphGPO)基于合并状态转移图分配信用，更适合状态可规范化、环境可重放的任务。两者均不应在首轮实验中与其他改动捆绑。

## 实验顺序与发表标准

1. **重建基线。** 固定模型权重、数据与语料哈希、检索器、提示模板、解码参数和工具预算。严格 EM、token F1 分别报告；历史宽松指标单列。保存逐题预测、完整轨迹与失败类别，先复核现成 checkpoint。
2. **验证训练链路。** 检查工具 token 的 loss mask、采样概率、分组索引、截断与停止行为；记录全同奖励组比例、有效组比例、梯度范数、entropy、KL、完成率及工具错误率。它们是诊断信号，不是单独的因果结论。
3. **单因素对照。** 顺序比较 GRPO 与 GiGPO；再单独比较 outcome-only 与步骤信用分配；mismatch correction 另做实验。每项至少三个训练随机种子，使用配对评估题、相同初始化与数据，并匹配 GPU 时间、生成 token、工具调用和 judge 预算。预算不能同时严格相等时报告质量—成本曲线。
4. **检验增益。** 报告跨种子均值与离散程度、题目级配对差值及置信区间；检查跨数据集、不同语料和更长交互下的结果。参数选择使用开发集，最终测试集独立保留。
5. **办公能力单独验证。** 把成功定义为文件或应用状态满足任务要求，同时约束非目标修改、调用成本与失败恢复。检索 EM 提升不等于办公可部署；更强模型接入首先作为推理基线，闭源普通 API 不提供本地 GRPO 所需的参数更新能力。

现阶段可公开的成果是清晰可测的执行与评估基础设施、独立旧代码修复和上述研究路线。只有完成新的受控训练与复核，才把具体能力提升写入结果表或项目摘要。
